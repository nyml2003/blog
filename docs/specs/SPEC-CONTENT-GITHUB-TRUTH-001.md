# 内容真源 GitHub 化

## 状态与目标

本修订记录 2026-09-06 用户确认的目标行为，等待实现和验收；不是当前代码已具备能力的声明。它替代旧版“保存即写 GitHub、凌晨重启、图片资产、存量迁移”安排。

私有 GitHub 仓库保存已提交内容；服务器维护临时工作区和已发布内容的持久缓存。日常操作为：后台编辑并保存，工作台整批提交 PR，用户在 GitHub 合并，再回后台同步。用户不直接编辑 GitHub 文件。

## 内容与存储

- 内容仓库布局固定为 `taxonomy.json` 与 `articles/<固定数字ID>/{meta.json,content.html}`。元数据与正文分别使用 JSON 和原始 HTML fragment，不使用 frontmatter。
- 类型、专题和标签集中放 taxonomy；文章元数据复用现有标题、摘要、类型、标签和服务器时间语义，摘要上限仍为 160 个 Unicode 字符。具体字段映射与读写样例由 REPO-CONTRACT 交付。
- 文章 ID 为稳定数字，重命名和正文编辑不改变目录、链接或引用；已使用 ID 不分配给另一篇文章。
- 首次发布时间以该文章第一次合入 `main` 的时间为准，由 GitHub 历史恢复，禁止用保存时间或首次同步时间代替。后续更新和同 ID 恢复不重置首次发布时间。
- `main` 当前存在的合法文章是已发布内容。工作区和未合并分支不能改变公开可见性；不以作者填写的 status 字段决定发布。
- 临时工作区与前台缓存分离。临时工作区的未提交改动允许在重启后清空；SQLite 前台缓存、同步版本及推荐状态必须持久保存。
- 没有存量内容迁移任务，初始化空仓库即可。初始化需生成合法空 taxonomy 并建立 `main`，不带测试文章或凭证。

## 保存与整批提交

- 编辑文章、类型、专题、标签和暂存下架都通过后台完成。保存只改变临时工作区，不写 GitHub，不改变前台；未保存的浏览器输入不属于待提交批次。
- 保存前服务器检查输入。非法 HTML 返回既有定位诊断，保存结果不变；前端保留输入供修改。不得静默改写或修复正文。
- 工作台读取工作区及与已同步内容的差异，集中展示待提交清单、当前 PR 和同步结果；没有逐项选择或单篇提 PR 功能。
- 提交包含所有已保存的待发布变化。以整批目标内容验证 HTML、元数据、重复 ID 和 taxonomy 引用，全部通过后才允许远程写入；一项失败则整批拒绝。
- 服务器全局只有一个活跃工作分支和对应批次。首次提交创建分支和 PR，后续提交在同分支更新原 PR；所有后台会话共用此工作区。
- 提交使用固定工作区版本，将整个批次作为一个 Git 提交更新分支。提交期间拒绝相冲突的写入；旧页面提交的过期版本必须返回冲突，不能覆盖后来保存的内容。
- 分支已更新而 PR 创建失败时记录“提交未完成”，重试恢复已有远程结果并继续创建 PR。超时结果先查明，不盲目新建分支或 PR，不强制覆盖未知远程变更。
- 恢复时发现多个无法判定归属的活跃分支则返回工作区状态错误；保留远程内容并停止新建，不自行挑选或删除。
- 服务器没有自动 merge 路径。用户合并 PR 后，必须同步成功才结束旧批次；期间新保存但未提交的改动保留到下一批。
- 放弃批次需显式确认。若存在未合并 PR，先确认关闭成功再清空工作区；失败则保留。已合并 PR 不可通过放弃撤销，需在下一批修改或下架。
- 启动时可以从 GitHub 分支/PR 恢复已提交内容，包括待补建 PR 的分支；未经远程确认，不在未知已有分支的情况下另开批次。

## 同步与故障

- 只有服务启动时的一次同步和后台手动同步；没有定时重启、定时同步、timer、cron、轮询、webhook 或 ops 同步命令。
- 两种入口复用 Product 的同步协调：固定 `main` commit -> 读取全套文件 -> 校验与解析 -> Data 单事务替换内容快照 -> 记录成功版本。
- 同一时刻只执行一次同步；重复请求返回进行中状态，重复导入同一版本的内容与时间结果一致。
- 下载、格式、HTML、引用、历史时间解析或数据库写入任一失败，整次同步失败，前台保留旧版，不导入部分合法文章。
- GitHub 或 PAT 故障不得导致已有前台缓存不可读或服务拒启。无历史缓存时提供空公开结果并报告尚未成功同步，不能伪装导入成功。
- 普通同步不清空临时工作区。合并后的批次收尾只在导入成功后发生，并保留上次提交之后新增的临时改动；冲突保留原工作区并返回错误。
- 推荐状态不因替换内容表而重置。下架文章从公开列表、详情和推荐展示中消失，其余推荐 ID 与顺序保留；再次上架不是新 ID。
- 后台显示同步状态、目标/成功 commit、内容数量和失败原因；前台只读取最后成功提交的快照。

## 层间接口与运行边界

- Product 负责 GitHub、工作区、共享 HTML core 校验和同步协调；Data 提供类型化事务操作，不解析 HTML 或访问 GitHub；Product 不直接访问 SQLite。
- 管理接口沿用 GET/POST、sceneCode 和响应 envelope。能力覆盖工作区/文章读取、保存文章与 taxonomy、暂存下架、提交批次、放弃批次、查询状态和手动同步；协议名称、DTO 与客户端映射统一由 REPO-CONTRACT 交付。
- 保存/提交/同步均为服务端权威检查。WASM 只改善编辑体验，未经校验的正文仍禁止进入可信预览路径；HTML Profile 保持 `article-html/v1`。
- 旧直接数据库保存、发布、取消发布和 taxonomy 写入口与前端一次性切换；不得遗留绕过 PR 的写路径。公共读接口、排序和 BFF 契约不变。
- 所有后台读取、保存、提交、放弃与手动同步均接入独立交付的管理鉴权；鉴权未具备时不得启用真实管理接口。认证实现不属于本计划。
- PAT 仅在服务器，通过 `BLOG_CONTENT_REPO` / `BLOG_CONTENT_TOKEN` 配置目标私有仓库；权限覆盖该仓库 Contents 读写和 Pull requests 读写，不进入前端、日志或错误原文。[GitHub PR 权限说明](https://docs.github.com/en/rest/pulls/pulls#create-a-pull-request)
- Data 的 prod 实现使用持久数据库，不加载 seed，不在正常退出时清理；路径遵守显式参数 > `BLOG_DATABASE_PATH` > 无默认值。生产数据放仓库外。
- mock/test 与 GitHub 来源模式显式隔离，开发入口不因存在 PAT 环境变量而连接真实仓库。真实验收使用独立测试仓库，生产启用另行交付。

Given 有旧前台缓存，GitHub 不可用或 PAT 缺失/失效
When 启动、提交或手动同步
Then 前台仍读旧缓存，服务不因远程故障拒启；需要远程操作的请求明确失败，凭证不泄漏。

### SPEC-CONTENT-GITHUB-TRUTH-001-007：退休

原旧 SQLite 内容迁移场景取消，使用空仓库初始化，不复用本 ID。

### SPEC-CONTENT-GITHUB-TRUTH-001-008：公开兼容

Given 新链路完成切换
When 访问 Desktop/Mobile 公开页面与既有公共 API
Then 可见性、排序、分页、筛选与 BFF 行为不变；项目质量门禁和浏览器回归通过。

### SPEC-CONTENT-GITHUB-TRUTH-001-009：错误保存

Given 编辑器有非法 HTML
When 点击保存或直接调用后台保存接口
Then 返回定位诊断，不修改临时工作区、GitHub 或前台；编辑器保留输入与上次保存结果。

### SPEC-CONTENT-GITHUB-TRUTH-001-010：批次校验

Given 批次含新类型及引用它的文章
When 提交
Then 按整个目标内容检查引用；任一 HTML、元数据或引用错误均使整批拒绝，不跳过错误项发布其他内容。

### SPEC-CONTENT-GITHUB-TRUTH-001-011：单分支与多页面

Given 已有开放 PR，两个后台页面使用同一工作区
When 再次保存和提交，或旧页面写入过期版本
Then 新保存仅留临时区，提交更新原 PR；过期版本返回冲突，绝不覆盖新保存结果。

### SPEC-CONTENT-GITHUB-TRUTH-001-012：提交恢复

Given commit 已写入但创建 PR 失败，或请求结果超时
When 重试或服务重启后恢复
Then 复用已有分支/PR，不重复创建、不强制覆盖未知内容；已写入 GitHub 的合法内容可恢复。

### SPEC-CONTENT-GITHUB-TRUTH-001-013：缓存生命周期

Given 同时存在未提交改动、已提交 PR、已发布缓存与推荐状态
When 服务重启
Then 未提交改动允许清空，已提交内容可恢复；持久公开缓存与推荐状态不丢失。

### SPEC-CONTENT-GITHUB-TRUTH-001-014：同步原子性

Given 已有公开快照，main 新版本中某项内容非法或 Data 事务失败
When 同步
Then 整次失败并保留旧快照与成功版本；不存在混合新旧内容或部分导入。

### SPEC-CONTENT-GITHUB-TRUTH-001-015：合并后的新改动

Given PR 提交后工作区又保存了新改动，该 PR 随后合并
When 手动同步
Then 成功后结束旧批次且新改动进入下一批；同步失败不结束旧批次、不清空工作区。

### SPEC-CONTENT-GITHUB-TRUTH-001-016：放弃批次

Given 尚未合并的批次
When 用户确认放弃
Then 关闭 PR 成功后才清空临时区，前台不变；关闭失败保留工作区，已合并内容不能由放弃操作撤销。

### SPEC-CONTENT-GITHUB-TRUTH-001-017：身份与时间

Given 文章首次合并后经历修改、下架、同 ID 恢复
When 同步或从 GitHub 全量重建缓存
Then ID、链接和首次合入时间稳定，不使用同步时间代替发布时间，也不复用 ID 给另一篇文章。

### SPEC-CONTENT-GITHUB-TRUTH-001-018：管理保护

Given 未认证调用者
When 请求工作区读取或任一管理写操作
Then 被鉴权拒绝；不能读取未公开内容、写 GitHub 或触发同步。已认证用户可走完整后台流程。

### SPEC-CONTENT-GITHUB-TRUTH-001-019：环境隔离

Given 开发/Mock/test 环境存在真实仓库与 PAT 环境变量
When 运行本地开发和自动化测试
Then 仍仅使用隔离样例与模拟 GitHub，不隐式访问真实仓库。

### SPEC-CONTENT-GITHUB-TRUTH-001-020：一次性切换

Given 新后台工作流启用
When 调用旧直接保存/发布/取消发布/taxonomy 写路径
Then 旧路径已退役，不能绕过批次 PR 改变前台或持久内容。
