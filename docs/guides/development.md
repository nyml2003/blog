# 开发指南

采用持续流，不强行凑固定 Sprint。小范围、单一写集的改动可以直接进入任务；跨模块、跨角色或需要明确取舍的工作，再建立轻量计划或任务记录，并拆成可验收的工作流。计划是协调工具，不是所有改动的前置门槛。

## 并行规则

- 产品、视觉、前端、BFF、后端、基建和运维可以作为不同 workstream；
- 每个任务声明 owner、依赖和 `write_set`；
- 不修改同一写集的任务可以并行；
- 写集重叠时先完成契约任务，其他任务等待；
- 早期用依赖和等待解决冲突，冲突增多后再使用分支或独立工作树。

## 完成条件

工作流完成必须提供实现、测试/验收证据、影响文档和未决项。涉及计划时，计划记录应明确哪些工作已完成、哪些部分暂停或被替代；当前架构按实际实现更新，稳定约束变化时修订 `FACTS.md`。
