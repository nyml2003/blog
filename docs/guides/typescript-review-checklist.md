# TypeScript Code Review Checklist

这份清单用于补足 lint、format 和类型检查不能可靠判断的认知问题。Review 先记录工具扫描结果，再逐文件检查以下项目；不要用“工具通过”替代人工判断。

## 控制流

- [ ] 失败、无效输入和不适用状态是否尽早返回？
- [ ] 主路径是否被多层嵌套包住？
- [ ] 三元表达式是否只有一个简单、纯值条件？是否存在嵌套三元？
- [ ] `&&`、`||`、`??` 是否只做值选择，没有隐藏副作用？
- [ ] 复杂条件是否已命名或拆成谓词函数？

## 类型和错误

- [ ] 可选值是否统一使用 `undefined`，而不是在领域层传播 `null`？
- [ ] 状态是否使用可辨识 union 或 `Result`，而不是真假值约定？
- [ ] 对象类型和函数入参是否明确选择了整体 `Required` 或整体 `Partial` 语义？参数列表是否避免混合必填和可选参数？混合可选性是否属于有名称、有边界的协议例外？
- [ ] 类型收窄是否通过可见条件完成？断言和非空断言是否有明确边界保证？
- [ ] 可预期失败和真正异常是否使用了清晰且一致的错误模型？
- [ ] `catch` 是否正确处理未知错误值？是否抛出了 `Error` 或明确的错误类型？

## 异步和副作用

- [ ] 每个 Promise 是否有明确的等待、取消或拒绝处理者？
- [ ] 并行和串行是否符合业务顺序要求？
- [ ] 重试、超时、取消和状态更新是否集中在协调层？
- [ ] 渲染、条件表达式或回调中是否隐藏了写入、请求或状态变更？

## 命名和职责

- [ ] 名称是否表达业务角色，而不是只描述容器形状？
- [ ] 函数是否只有一个主要职责？
- [ ] 是否把校验、协议转换、领域操作和 UI 更新混在同一个函数？
- [ ] 是否存在可以命名的重复条件、魔法状态或隐式约定？

## 测试、脚本和工具

- [ ] 测试是否清楚表达场景、边界和失败原因？
- [ ] fixture 简写是否仍保持输入和断言的可读性？
- [ ] 脚本副作用是否集中在明确的适配层？
- [ ] 工具代码是否保留了错误、退出码和资源清理路径？

## 例外记录

每个偏离“必须”规则的例外都必须写明：

- 适用文件或最小代码范围；
- 偏离的具体规则；
- 为什么显式写法会更差，或为什么边界条件已由外部系统保证；
- 如何证明不会把例外扩散到领域层；
- 关联的 issue、Spec 或后续专项任务。

全局关闭规则、无理由的 `eslint-disable`/`oxlint-disable` 和“以后再处理”不属于有效例外。

## Review 结论

Review 结果必须同时记录：工具扫描命令及结果、人工发现、已处理项、批准例外、测试证据和未决项。未执行人工 Review 时，不得以 lint、format 或 typecheck 全绿作为可读性验收结论。
