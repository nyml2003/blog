# Mobile 体验优化

## 范围变更记录（2026-09-30 收尾时补记）

本计划立项时按"先完整审计 9 项旅程、过决策闸门、再实现"设计。实际执行中，产品（站长）带着真实部署后的两个具体问题直接进入决策：先共同建立度量能力并确认指标集，再按数据授权实施两项 P0 优化。收尾时产品明确决策：

- 本轮范围收敛为：`ops perf mobile` 度量能力 + 基线、静态缓存与 gzip、site-routes 构建期内嵌；全部交付、验证并随 build-v0.1.6 发布。
- P1 底栏静态骨架：明确暂缓，视真机效果再定。
- 原"探查阶段"9 项审计清单与决策闸门的其余产品题（详情页返回策略、横屏、F 型分类结构等）**整体移出本计划**，由后续 Mobile 体验计划以本目录 RESULT.md 为输入接手。
- 复盘教训：立项范围过宽（审计先行 + 全旅程 + 决策闸门一次性打包），后续同类计划应按"一次一个可验收的具体问题"立项，避免计划天然无法以 completed 收尾。

以下原文保留不动，作为当时的范围承诺与二期输入的历史记录。

## 目标

系统探查并改善 C Mobile 的真实使用体验，重点关注打开、浏览、筛选、阅读、返回、设置和异常恢复等连续旅程。具体改造范围不在立项时预先拍板，由接手本计划的实现 agent 先完成体验审计，再和产品共同确认优先级与验收标准。

本计划先建立问题事实和候选方案，再进入实现；不把“移动端体验优化”直接等同于换颜色、加动画或继续迁移代码。

## 当前基线

- 公开 Mobile 首页、文章库、检索、详情和设置已经使用新 `app/bootstrap/mobile` 与 `app/habitat/mobile` 运行时。
- Mobile 的页面、UI、手势、主题和状态反馈有现行架构约束，但仍存在新旧实现、管理预览和迁移中的样式兼容边界。
- 当前 UI/UX 基线要求：触控目标至少 44px、不依赖 hover、详情页不显示底栏、分类选择支持 URL/history、加载/错误/空状态稳定、正文不可造成页面级横向滚动、支持 reduced motion。
- 现有测试主要覆盖逻辑、边界和源码依赖；体验问题仍需要真实窄屏/宽屏浏览器、键盘/触控模拟、网络异常和截图对照来确认。
- 加载性能度量能力已建立：`ops perf mobile`（冷加载/底栏切换 × unthrottled/slow4g/slow3g 网络档位，指标含壳/内容可见耗时、FCP/LCP、传输字节与缓存命中）。2026-09-30 基线见 [BASELINE-PERF.md](./BASELINE-PERF.md)：所有档位缓存命中 0/9，每次切换全量重下约 183.6KB，slow3g 下切换页面中位 5.9s。

接手 agent 的第一轮探查已发现以下候选问题，尚未视为已批准改造：

- 现有 E2E 主要覆盖部分文章旅程，缺少首页、设置、Mobile 预览、横屏、主题/字体组合和系统化视觉基线；
- F 型分类货架的原生按钮需要核对选中组语义、读屏状态、长分类名、横向滚动和 safe-area；
- 文章卡片的更新时间使用字符串截取，详情页使用本地化格式，两处展示语义可能不一致；
- 页面已有部分 loading/error/empty/retry，但设置失败、离线和跨页面错误恢复不统一；
- `mobile-ui` 与 `app/habitat/mobile/ui` 双份组件，以及旧 Mobile 管理预览链路，可能造成视觉和交互漂移；
- 详情页无底栏、三项底栏、是否支持横屏、是否增加搜索/分享/收藏等仍属于产品决策，不由本 Plan 默认增加。

## 探查阶段

接手 agent 必须先提交一份体验审计，再开始代码改造。审计至少覆盖：

1. 首次打开、刷新、直达带参数 URL、弱网和 API 失败；
2. 首页发现内容、进入文章库、一级/二级分类切换、前进/后退和分享链接；
3. 文章详情首屏、返回、长正文、代码块、表格、图片和阅读连续性；
4. 设置读取、切换、保存失败、恢复默认和跨页面首绘；
5. 空数据、错误、重试、取消和快速重复操作；
6. 375px、390px、430px 等窄屏，以及较大 Mobile viewport；
7. 触控目标、读屏名称、焦点、对比度、减少动画和横向溢出；
8. 真实网络请求数量、首屏阻塞、重复请求、取消和过期响应；
9. 新运行时页面与仍存在的旧 Mobile 预览/兼容样式之间的体验差异。

审计结果必须把问题分成：

- 事实缺陷：可以由代码、测试或浏览器复现；
- 体验风险：需要用户或设计判断；
- 架构问题：页面编排、组件、数据或导航职责不清；
- 暂不处理：收益不足、依赖未满足或属于其他 Plan。

## 候选优化方向

以下只是探查清单，不是预授权范围：

- 首屏加载和首绘：减少阻塞、稳定 skeleton/状态高度、避免主题闪烁；
- 浏览效率：底栏、分类货架、文章卡片、筛选和返回路径的可发现性；
- 阅读体验：标题区密度、正文宽度、代码/表格/图片、返回入口和长文滚动；
- 状态恢复：URL/history、刷新、分享链接、网络失败和重试后的状态保持；
- 触控与可访问性：命中区域、焦点、读屏名称、对比度、动态字体和 reduced motion；
- 性能与网络：请求瀑布、缓存、取消过期请求、慢网络提示和资源体积；
- 组件一致性：页面状态、按钮、输入、标签、导航和错误提示的语义与几何稳定；
- 迁移收敛：删除旧 Mobile 页面/组件造成的双重样式和行为差异。

## 决策闸门

体验审计完成后，接手 agent 与产品共同确定：

- 本轮最多 3 个主要用户问题；
- 每个问题的目标用户旅程和可观察指标；
- 是否允许视觉变化、信息架构变化或 API/协议变化；
- 哪些问题归入前端架构清理 Plan，哪些留在本 Plan；
- 详情页返回采用浏览器 history 还是固定文章库回退；
- 是否允许改变现有 F 型分类结构、三项底栏和详情无底栏规则；
- 是否纳入 Mobile 管理预览，以及目标设备、浏览器和最低性能指标；
- 浏览器、真机或截图验收的最低证据；
- 是否需要新增 Spec、设计决策或单独的性能预算。

当前建议的优先级供讨论：

- P0：建立 375x812、390x844、412 宽度和横屏的 Playwright/截图基线，覆盖导航、分类、详情返回、状态和设置；
- P1：修正分类控件语义、时间展示、离线错误和重试反馈，并处理明确的窄屏/safe-area 问题；
- P1：决定旧 Mobile 预览和双 UI 是否在本 Plan 清理，或交由 Frontend 架构清理 Plan 串行处理；
- P2：优化长文阅读、代码/表格/图片、首绘、缓存和慢网络体验；
- P3：单独讨论搜索、分享、收藏等新产品能力，不默认混入体验优化。

未通过决策闸门前，Plan 状态保持 `discovery`，不得把候选方向当成已承诺功能。

## 约束

- Desktop 与 Mobile 不共享 JSX、CSS、DOM 或组件内部状态。
- 页面不直接访问 transport、storage、wire DTO 或具体 URL；体验优化不能绕过新运行时边界。
- 不为视觉问题擅自改 API、后端语义、文章可见性或路由契约。
- 不以构建通过代替浏览器体验验收；至少记录真实 viewport、网络条件、交互结果和截图或等价证据。
- 不默认引入新的 UI 框架、状态管理器、图标库或性能监控平台。
- 与 Frontend 架构清理、图标控件、E2E 计划存在写集重叠时，必须先协调并串行修改。

## 成功标准

1. 完成 Mobile 全旅程审计，并能区分事实缺陷、体验判断、架构问题和暂不处理项。
2. 产品确认本轮优先问题、目标旅程、非目标和验收证据后，Plan 从 `discovery` 进入可执行状态。
3. 优化后的关键旅程在窄屏、较大 viewport、正常网络和受限网络下均有可复现验收记录。
4. loading、success、empty、error、retry、取消、返回和 URL/history 行为有明确证据；不以“看起来正常”替代状态覆盖。
5. 触控、键盘/读屏、对比度、动态字体、reduced motion 和横向溢出检查通过，或明确记录未支持项及原因。
6. 相关前端测试、typecheck、lint、format、build 和必要的 `ops quality check` 通过。

## 集成验收

1. 使用 Playwright 或项目现有 E2E runner 验证首页 → 文章库 → 筛选 → 详情 → 返回的完整旅程。
2. 分别模拟正常、慢速、断网、接口 4xx/5xx、空数据和快速重复点击，检查状态稳定性和恢复动作。
3. 在至少 375px、390px、430px 宽度下检查布局、触控命中、标题换行、正文、代码块、表格、图片和页面横向滚动。
4. 验证刷新、直达 URL、分享 URL、前进/后退、主题设置和首绘样式保持一致。
5. 运行相关测试和构建；将自动化证据与人工视觉/交互证据分开记录。

## 收尾

本 Plan 可以以 `completed`、`partial`、`parked` 或 `superseded` 收尾。收尾必须记录审计发现、实际交付、未处理问题、验收证据、停止或替代原因，以及恢复工作所需条件。
