# 内容真源 GitHub 化（临时工作区 + 整批 PR + 手动同步）

## 目标与当前进度

按 [SPEC-CONTENT-GITHUB-TRUTH-001](../../../specs/SPEC-CONTENT-GITHUB-TRUTH-001.md) 交付以下流程：

```text
后台编辑 -> 保存到服务器临时工作区 -> 工作台整批提交一个 PR
-> 用户在 GitHub 手动合并 -> 后台手动同步 -> 前台更新
```

计划目标是以私有 GitHub 仓库作为已提交内容的真源，服务器保存临时工作区、前台持久缓存和推荐状态。2026-09-07 按用户要求以部分交付状态归档；完整流程尚未实现，归档不表示验收通过或允许发布。交付范围与未完成项见 [RESULT.md](./RESULT.md)。

## 本轮已交付

- Data `prod` 使用显式持久 SQLite 路径，自动迁移、不 seed、正常退出不删除数据库；已有前台缓存可跨重启保留。
- Product 对内容仓库布局提供完整解析与写回校验，拒绝非法 HTML、重复/不一致 ID 和缺失 taxonomy 引用，并保留原始正文。
- Product 创建/更新入口在调用 Data 前拒绝非法 HTML；错误不会改变文章保存结果。
- Mock Product 与 Product 对齐同一保存门禁，并有契约测试证明非法创建/更新不会改变工作状态。
- Product 已有服务器临时工作区核心和隔离模拟远端：版本冲突、整批校验、单活跃分支/PR、重复提交更新原 PR、放弃先关闭 PR，以及同步单实例/失败保留上次成功版本均有纯函数测试。

上述交付仍未接入认证 HTTP、真实 GitHub transport、Data 快照替换事务或后台工作台；在这些依赖完成前不得将本计划标记为可发布。现有管理端合法保存和发布仍走旧 Data 流程，尚未达到保存与公开快照隔离的目标。命令和限制见 [EVIDENCE.md](./EVIDENCE.md)。

## 决策记录（2026-09-06 用户确认）

1. 文章、类型、专题、标签和下架操作全部在后台完成；用户不直接编辑 GitHub 文件，只查看和合并 PR。
2. 保存只进入服务器临时工作区，不产生 GitHub 写入，不改变前台；错误正文禁止保存，编辑器保留输入和诊断，上次保存结果不变。
3. 工作台一次提交全部已保存且尚未发布的改动；一个批次可以包含多篇文章、分类变化和下架，不提供逐项选择或每篇文章单独提 PR。
4. 服务器同时只有一个活跃工作分支，所有后台页面共用工作区。首次提交创建分支与 PR，后续提交更新原 PR；PR 开放期间继续保存仍只更新临时工作区。
5. 服务器永不自动合并；只有 `main` 同步成功的内容对前台可见。
6. 删除定时重启设计；同步仅在服务启动时执行一次，或由后台手动触发。没有 timer、cron、定时同步、轮询、webhook 或 `ops content sync`。
7. 未提交的临时改动允许在重启后清空；已写入 GitHub 的分支/PR可恢复。前台上次成功同步的缓存与推荐状态必须跨重启保留。
8. 仓库布局为 `taxonomy.json`、`articles/<固定数字ID>/meta.json` 和 `content.html`；正文和元数据分开，不使用 frontmatter。
9. 首次发布时间取文章第一次合入 `main` 的时间；更名、编辑、下架后恢复和缓存重建不改变 ID 或首次发布时间。
10. 当前没有存量内容，本期从空内容仓库开始，不实现旧 SQLite 内容导出或迁移工具。
11. 图片完整链路延期；不做上传、release 资产、图片代理缓存或 HTML Profile 图片扩展。
12. 登录独立交付，真实后台操作启用前必须受保护；编辑器改造等待 `PLAN-DESKTOP-EDITOR-001` 归档。
13. 管理写流程与前端一次性切换，旧直接保存到数据库并发布的入口不保留兼容期；公共读接口和 Desktop/Mobile 公开行为保持现有契约。
14. 开发、Mock 与自动化测试使用隔离样例和模拟 GitHub；真实链路验收使用独立测试仓库，不隐式使用真实内容仓库和 PAT。

以上记录替代原版本中的保存即写分支、凌晨重启、图片链路、存量迁移和待选择手动同步入口等安排。

## 补充执行默认值

- 提交前检查整批目标内容，错误时整批拒绝；通过后以一个 Git 提交更新分支。请求重试不得重复创建分支/PR，远程状态不确定时先恢复状态。
- 提交期间固定工作区版本；其他写请求返回忙碌/版本冲突，不覆盖新改动。同步单实例执行，成功前前台一直读取旧版本。
- PR 合并后先同步；成功后结束旧批次。合并后新保存但未提交的变化带入下一批；普通同步不清空工作区，失败不清空任何已有结果。
- 工作台提供经明确确认的“放弃批次”：未合并 PR 关闭成功后才丢弃对应临时工作区；已经合并的内容只能通过下一批修改或下架。
- 推荐状态独立于导入内容保存；下架文章不再对外展示或出现在推荐结果中，其他推荐 ID 与顺序不被重建重置。
- 服务启动恢复分支/PR 状态；恢复失败不影响前台旧缓存，但不得在未知已有分支的情况下另建活跃分支。

## 原定验收

以下是原定验收要求，尚未全部达成。本次按用户要求结束计划并归档，不替代功能验收；具体证据与缺口见 [RESULT.md](./RESULT.md)。

1. [部分] Product 非法文章创建/更新返回定位诊断且不写 Data；工作区核心同样拒绝非法保存。前端编辑器、认证 HTTP 和 GitHub 零写入证据待交付。
2. 多文章、新分类和下架整批提交，同分支更新同一 PR；任一内容错误不会产生部分提交。
3. 提交超时、创建 PR 失败、重复点击和重启恢复均不产生第二个活跃分支；能从已写入的分支继续完成 PR。
4. 未提交临时内容重启可丢；已提交内容可恢复；前台缓存与推荐状态持久保留。
5. 手动同步和启动同步复用同一导入流程；GitHub/PAT 故障、解析/校验/存储失败保留旧快照，重复同步结果相同。
6. 固定文章 ID、首次合入时间、下架可见性、推荐过滤及合并后未提交改动保留正确。
7. 真实测试仓库完成“后台保存 -> 整批提交 -> 人工合并 -> 手动同步 -> 前台更新”，验证管理鉴权及 Desktop/Mobile 公开页面回归。
8. 在项目 Flake 中完成 Rust fmt/clippy/test、前端 typecheck/lint/format/core tests/build、ops 契约测试；实际命令、结果与环境问题分别记录。
9. Spec 场景逐项映射证据后才推进验收与归档；旧场景 004（图片）和 007（旧数据迁移）明确退休，不复用 ID。
