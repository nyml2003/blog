# C Mobile 视觉前置审计

## 初步结论

当前最值得优先优化的是文章详情页。问题主要是“进入正文前的有效信息不足”，而不是正文排版本身过于宽松。标题区、返回操作、装饰分隔和底部留白叠加，推迟了正文的到达；同时文章类型和更新时间等元数据不足以帮助用户判断文章价值、状态和上下文。

## 页面现状

### 推荐首页 `/m/`

页面结构：品牌 Header -> 页面眉题/标题/说明 -> 推荐文章列表 -> 浏览全部文章 -> 底部导航。

当前主要观察：文章条目本身信息相对完整，但页面标题说明和主操作占据了连续的非内容空间；是否需要压缩要等详情页基线确定后比较。

### 文章库 `/m/articles/index.html`

页面结构：品牌 Header -> 页面标题/总数 -> Filter 触发器 -> Shelf 左侧分区索引 -> 分区文章条目 -> 底部导航。

当前主要观察：Filter 和 Shelf 的信息密度问题仍然存在，但属于独立的筛选/扫描工作流，不应与详情页正文进入问题混合处理。

### 文章详情 `/m/articles/detail.html`

页面结构：阅读 Header -> 返回文章按钮 -> 类型眉题 -> 标题 -> 摘要 -> 更新时间 -> 装饰分隔线 -> HTML 正文 -> 底部返回/品牌信息。

## 详情页问题清单

### P0：正文进入路径偏长

- 顶部阅读 Header、页面 padding、返回按钮的下间距、标题区 padding/margin 和分隔装饰连续叠加；
- 用户在看到正文前需要经过多个低信息密度节点；
- 详情页的主要任务是阅读，正文应更早进入首屏。

候选方向：合并阅读 Header 与返回操作；减少重复返回入口；压缩标题区垂直间距；将装饰分隔降级为低占位语义边界。

### P1：元数据的信息价值不足

- 目前详情页主要显示文章类型和更新时间；
- 主题/标签、创建时间或文章状态等上下文没有形成稳定的阅读前摘要；
- 空间被占用，但用户得到的判断信息有限。

候选方向：在不增加大块卡片的前提下，增加一行紧凑元数据；只保留能帮助判断和回溯的字段；不要把列表页的全部元数据原样复制到详情页。

### P1：标题区层级偏重

- 移动端标题使用较大字号和较宽行高，长标题会进一步推迟正文；
- 摘要使用较大的字号和行高，但摘要不是所有文章都有；
- 无摘要时标题区的空白比例会更明显。

候选方向：保留标题的阅读优先级，但为长标题设定稳定的最大行数或更紧凑行高；无摘要时收紧标题区；不要用占位文案制造虚假信息。

### P1：阅读过程中的导航不足以支持长文

- 当前只有顶部返回和底部返回，没有文章内目录、阅读进度或相邻文章入口；
- 对短文影响不大，对长期知识库中的复杂排查文章可能不足；
- 这属于阅读效率增强，不应在本轮与密度压缩同时全部实现。

候选方向：先验证文章长度和结构，再考虑轻量目录或顶部进度；相邻文章导航延后到独立计划评估。

### P2：底部返回信息重复

- 顶部已有返回文章库/返回文章操作，底部再次提供返回入口；
- 对短内容是重复占位，对长内容才可能有价值；
- 当前底部同时放置品牌信息，信息优先级不够明确。

候选方向：保留符合长文习惯的底部返回，但降低视觉重量；或根据正文长度决定是否显示，避免固定占位。

## 优先级建议

```text
第一轮：压缩正文进入路径 + 重排详情元数据
第二轮：长标题/无摘要/长文状态下的稳定布局
第三轮：阅读进度、目录、相邻文章等效率能力
```

## 暂不建议

- 直接把正文字号压到不可读；
- 用更多卡片、边框或装饰填补空白；
- 把文章列表的所有字段复制到详情页；
- 在没有长文数据证据前加入复杂目录或浮动工具栏；
- 为了详情页优化同时重做推荐和归档页。

## 下一步

1. 用真实文章数据记录短标题、长标题、有摘要、无摘要、短文和长文六类视口；
2. 统计正文首屏前的垂直空间占比；
3. 由产品确认详情页首屏必须保留的字段；
4. 视觉提出一版低风险结构调整，再决定是否进入实现工作流。
