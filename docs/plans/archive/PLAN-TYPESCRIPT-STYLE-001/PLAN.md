# TypeScript 代码可读性规范

## 目标

建立一套以降低认知复杂度为目标的 TypeScript 开发规范。规范优先强调显式控制流、早返回和可读命名，不把代码风格简化为“禁止某个语法”。首期只定规范并完成评审，现有代码按后续计划逐步整改。

## 成功标准

- 规范覆盖项目内前端、测试、脚本和工具 TypeScript 代码；
- 明确 if 卫语句、三元表达式、`&&`、`||`、`??`、异常和 `Result` 的使用边界；
- 规范能指导 code review，并包含正反例和可接受例外；
- 规范不要求一次性修改存量代码；
- 新增代码从规范生效后遵循规范，存量整改按独立计划分批进行；
- 机械规则交给现有的 `oxlint`、`Biome` 和 `tsc`，认知复杂度和业务表达由 review 与测试保证。

## 非目标

- 不在本计划中整体重写或格式化现有 TypeScript；
- 不把所有三元表达式、`&&`、`||` 或 `??` 设为禁用语法；
- 不用 ESLint 规则替代设计判断；
- 不规定与可读性无关的个人偏好，例如强制某种括号或文件命名风格，除非现有项目已有约定；
- 不改变业务行为、领域协议或 UI 架构。

## 约束与依据

- 事实：`FACT-PRODUCT-001`；
- 现有项目语言：TypeScript/Solid/Vite；
- 风格目标：减少嵌套和隐式分支，让错误路径、边界条件和业务意图可独立阅读；
- `undefined`/`null` 规则与客户端数据层协议保持一致：领域协议不使用 `null`，可选值使用 `undefined`；
- 规范首期是文档和评审产物，整改另立计划。

## 已确认原则

- 优先使用 if 卫语句尽早返回、尽早失败；
- 允许三元表达式、`&&`、`||`、`??`，但避免在一个表达式中叠加多个隐式分支；
- 不使用短路表达式隐藏副作用；
- 复杂条件拆成命名布尔值或独立函数；
- 业务状态优先使用明确的 union/Result，而不是真假值约定；
- 类型收窄和错误处理要让分支边界显式可见；
- 简单、无副作用的表达式可以保持简洁；
- 测试代码、脚本和工具代码遵循同一认知复杂度原则，按场景定义少量例外。

## 集成验收

1. 规范文档覆盖条件分支、空值、错误、异步、类型、命名、函数职责和测试代码。
2. 每条高影响规则至少有一个推荐例子和一个反例。
3. 规则明确“必须”“建议”“允许”和“例外”，不留下只凭个人理解的模糊禁令。
4. `oxlint`、`Biome` 和 `tsc` 只承载可机械判断的规则；无法可靠机械判断的规则进入 review checklist。
5. 规范发布后，新代码开始遵循；存量整改拆成独立、可回滚、可验收的后续计划。

## 移交项

- 工具配置、规则试运行、误报基线和质量门禁落地移交后续治理计划；
- 存量 TypeScript 全量整改顺序和执行由后续治理负责人制定；
- 是否引入认知复杂度静态分析工具由后续治理计划评估，不在本计划内决定。
